# 图片解释与回答核验改进

日期：2026-10-23。已实现并启动最新后端。本次后端全套245项通过，Ruff/格式与前端构建通过；SQL图片普通/思考模式、课程结合、刷新追问均有真实模型结果，另有两种模式下的受控错误候选修复验证。保留原失败，不改用户原消息、课程、密码或密钥。

## 改动

- 同一Agent按任务选择直接解释或课程检索。用户仅问图片/代码含义时，提示先给主旨及必要分层，不自行推断建表、外键或教材背景；未要求课程依据时无需强制检索或联网。
- 从**实际送给生成模型的用户输入块**建立本请求核验上下文：保留已纳入预算的图片、对应问题及有限追问文字，不在核验时重新加载其他图片，不把助手私有协议当作用户依据。只依赖图片的答案也进行图文语义核对，不强制其附课程引用。
- 新增`answer_review.py`：结构化核验结果为passed、needs_revision、insufficient_evidence，逐项记录断言、问题类型、简短原因；区分引用不支持、图像不符/模糊及推导错误。历史模型输出`{"supported":bool}`仍可读取，旧false没有具体理由时如实标记通用原因。
- 核验异常、超时或JSON不合法标记为`check_unavailable`，对用户返回“回答核对暂未完成”，stop_reason为verification_unavailable，不再当成内容已判错。
- 语义核验失败后至多一次修正、一次复核。修复使用本条不可变Agent思考配置；两次核验均关闭思考。它们共享原整轮截止与取消对象，未增加工具权限或路由模型。
- 修复修改/移除无依据断言，不能仅删除引用标记。程序拒绝“仅删除引文”的相同正文；仅凭图片重写的解释须再次核对图片与原问题。没有图片的来源事实不能通过删引用转成普通答案；严格课程和已读外部来源仍保持引用要求。
- 在首次核验后、修复后、复核后重新检查原来源及新引用的当前权限/状态。来源在修复期间删除或撤销时，不继续把失权正文带入第二次核验，最终不落入成功答案。
- `protocol_state.version=2`新增可选私有validation记录，保存实际候选、核验输出及修复调用。公开接口不返回这些内容。修正后与原协议末条答案不同则replayable=false，历史按既有兼容逻辑恢复展示答案，不伪造或重放错误候选的思考协议。无需schema迁移。
- 进度说明改为“正在核对图片、回答与来源，必要时修正一次”。普通失败提示不再统称“可靠的课程结论”。

## 保留的失败和局限

- 第一轮（本机原始材料，未随公开仓库发布）：HTTP/流程检查虽然通过，但Codex阅读发现普通模式回答把“达到平均”错误扩展成“排名前一半”。因此没有把“能回答”当成“全文事实正确”。这个结果促使本次把无引文图片答案也纳入图文核验。
- 第二轮（本机原始材料，未随公开仓库发布）：图文核验已接入，所有流程检查通过；仍发现思考模式附加的“一定不会正好一半”表述不严谨，核验器也未拦住。随后加强必要性/简洁性提示及平均值/排名、绝对断言的核验要求。保留该原结果，不覆盖。
- 最终回归（本机原始材料，未随公开仓库发布）：4条自然回答与2条受控修复程序检查通过。AI阅读确认核心SQL含义、平均对象、>=和例子一致，未再出现上述排名断言。回答仍可能比约300字提示更长；未把提示长度当成硬保证。
- 浏览器首轮只断言“部门”，实际模型用了同义的“系”，因此脚本失败。原错误与截图保留；断言允许同义表达后真实流程通过。见原失败（本机原始材料，未随公开仓库发布）、回归（本机原始材料，未随公开仓库发布）及最终浏览器记录。
- 新增图片核验会增加一次模型调用；触发修复时最多再增加两次。共享原截止时间，未声称延迟零增加。二次仍不支持、图像不清或核验不可用时会明确限制/澄清，不无条件放行。
- 语义支持关系由AI评估，仍可能漏检/误判；程序严格保证来源权限、注册编号、次数、截止/取消与引文保留边界，不声称形式化证明所有自然语言/SQL解释正确。

所有原结果及检查分别保存在本目录。最初增加图文核验后有一项测试仍要求“没有任何trace”，实际新增核验trace，已修正为“无工具调用且有核验”；原243/244结果保留在pytest-image-review.txt。最终245项日志为pytest-delivery.txt（本机原始材料，未随公开仓库发布）及XML。

## 使用与复现

服务端已重启，前端地址`http://127.0.0.1:5173/`。用户重新发送原SQL图片和问题即可，旧失败消息按历史事实保留。无需修改.env、重建资料或执行新迁移。

```powershell
# backend，要求API/Worker/PostgreSQL/Redis正常
uv run --no-sync python -m scripts.accept_answer_review
# frontend，使用上条命令输出的context绝对路径
$env:ANSWER_REVIEW_CONTEXT='<本次context.json>'
npx playwright test e2e/answer-review.spec.ts --reporter=line
# backend，验收完成后只清理该隔离上下文
uv run --no-sync python -m scripts.accept_answer_review --cleanup <本次context.json>
```

清理仅针对上述三轮生成且记录的隔离用户ID，先核对邮箱/run一致，再删除其自有资源。报告、原始结果、自制图片及截图保留；具体完成记录见各运行目录cleanup.json。未删除用户的原失败记录或私人资料。
